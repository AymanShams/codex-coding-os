  - Automation-Preserving Case Orchestration Policy: Parent orchestration and child agents are enabled only inside an explicitly approved run envelope bound to one canonical case ID. The parent is administrative only. A case permits one implementation generation, one frozen-head review cohort, at most one explicitly authorized combined repair, and one closure check. A new chat, branch, worktree, pull request, commit counter, or child session cannot reset the case. The case-state engine is the lifecycle authority and prose files are mirrors. A stop or red lock is case-scoped and unrelated work remains available.
  - `ANTI_LOOP_LATCH` is a canonical engine state, not advisory prose. It has higher precedence than every ordinary workflow, case-transition, state-sync, review, handoff, session, branch, pull-request, CI-monitoring, installation, or coordination gate. An otherwise mandatory support gate cannot authorize work after the latch fires.
  - The engine must latch the exact case when any of these occurs: the same support-failure fingerprint repeats; a second consecutive support mutation is attempted without an intervening product-head advance; a support step proposes another support-only task, case, branch, worktree, handoff, review, repair, installation, or authorization cycle; or a caller-declared actor role contradicts the controller-bound thread identity.
  - Once latched, deny every mutating or support action before evaluating ordinary workflow eligibility. Permit only read-only status and evidence inspection plus one exact human disposition: `STOP_CASE` or `SHIP_PRODUCT_WITH_CONTROL_QUARANTINED` at the recorded product head. The agent must not create, infer, draft, solicit, or self-approve an override.
  - A new chat, session, agent, branch, worktree, pull request, manifest, handoff, commit, retry counter, installation, or repository-local state file cannot clear or replace the latch. The protected external case store is authoritative. Repository files may mirror the decision but cannot reset it.
  - Every canonical case-state or support mutation requires a one-use request ID bound to the controller-verified actor thread, controller-assigned role, exact case revision, and exact applicable repository, branch, worktree, and product-head context. Any brokered protected-file replacement additionally requires a one-use action grant bound to the exact target and replacement digest. Ordinary product-file editing in a `CLEAR` case remains governed by its approved product scope and must not be reclassified as a support mutation. Caller-declared roles, unbound threads, actorless grants, and action checks without thread identity fail closed.
  - Before the latch fires, source checks, state files, reviews, validation, handoffs, and coordination remain support steps only when they directly complete the requested outcome or prevent a concrete source-of-truth or verification error. They must never expand into a second support generation.
  - Review completion gate: The parent must declare the exact required review cohort, frozen head, snapshot, canonical reviewer thread, controller-observed native child and parent thread identities, exact scope string, and scope digest before collection. The completion mutation accepts only the frozen reviewer identifier. The engine derives the receipt from that child's authenticated native rollout, exact ordered task completion, and raw final v2 payload. Caller-supplied role, thread, findings, completion state, timestamp, or evidence digest cannot substitute. Findings cannot freeze, enter closure, or authorize publication until every required reviewer has one natively verified canonical `COMPLETED` receipt matching the assignment. Persisted v1 receipts require a same-rollout native restatement attestation that preserves the original receipt digest. Missing, unverified, failed, incomplete, stale-head, wrong-scope, or wrong-thread receipts deny the transition without consuming another cohort.
  - Proposal-only model boundary: Codex App Server parents and children are identity and proposal workers only. They run read-only with network disabled, `approvalPolicy=never`, `dynamicTools=[]`, no MCP servers, no hooks, no inherited tool environment, and no exposed command or file-mutation approval. Native thread evidence never grants write authority, and model-provided roles are ignored.
  - Exact runtime action boundary: A reviewed deterministic supervisor and a distinct broker principal may authorize only one presealed replacement of one existing tracked file. The canonical grant must bind the exact case, controller-assigned implementer thread and completed turn, repository, branch, worktree, base head, target path, baseline and replacement digests, controller receipt, worker and broker SIDs, expiry, isolation evidence, and pinned controller sources. Parent, reviewer, closure, incomplete, and unknown identities receive no mutation grant.
  - Operating-system enforcement: The target, canonical state, controller source, and dedicated nonoverlapping proposal roots plus their immediate parents must be broker-owned and explicitly deny the worker write, delete, delete-child, permission-change, and ownership-change capabilities. Root creation, nested creation, exact-anchor overwrite, replace, rename, delete, hard-link, ACL-change, and owner-takeover probes must all fail with access denied while challenge paths remain absent and anchor hashes, identities, and security-descriptor hashes remain unchanged. A broker claim authorizes a write only when the canonical response is non-idempotent.
  - Active-grant barrier and recovery: While one grant is issued or claimed, unrelated case mutations are denied without revision change. A broker restart may resume once only from protected journal evidence and an exact baseline, or complete an already exact replacement without rewriting. Any mismatch, second recovery, preclaim failure, supervisor-context loss, rollback failure, or attempted replay consumes the grant and locks only that case. No grant is released or reissued.
  - Access-control transaction and startup gate: The broker must journal the exact original descriptors and lockdown intent before changing any protected access control list, keep lockdown active through post-replacement dual-profile probes and canonical completion, then restore parents before children. Startup must resolve pending lockdown, active-grant, completed-grant, and partial-restore state before schema inspection or App Server launch. A no-grant case may start only from `IMPLEMENTING`. Recovery after a pre-grant lockdown restores the exact snapshot, terminally consumes that generation, and locks the case without issuing a grant.
  - Terminal quarantine: A proven erroneous `CLOSED_SUCCESS` may be moved only to `CASE_LOCKED` through the one-use audited quarantine operation bound to the exact revision and case-record hash plus named human authority. Quarantine preserves all lifecycle counters, writes an exact protected backup and hash-chained audit, never reopens the case, and records whether external reconciliation is required.
  - Narrow scope: The single-file replacement broker is feasibility coverage for this exact primitive. It is not authority or evidence for arbitrary commands, file creation, deletion, rename, multi-file patching, general coding, publication, merge, deployment, credentials, or universal synchronization.

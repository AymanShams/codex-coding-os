  - Automation-Preserving Case Orchestration Policy: Parent orchestration and child agents are enabled only inside an explicitly approved run envelope bound to one canonical case ID. The parent is administrative only. A case permits one implementation generation, one frozen-head review cohort, at most one explicitly authorized combined repair, and one closure check. A new chat, branch, worktree, pull request, commit counter, or child session cannot reset the case. The case-state engine is the lifecycle authority and prose files are mirrors. A stop or red lock is case-scoped and unrelated work remains available.
  - Review completion gate: The parent must declare the exact required review cohort, frozen head, snapshot, canonical reviewer thread, exact scope string, and scope digest before collection. In a live App Server run, each reviewer thread must first be bound from controller-observed native identity evidence. Findings cannot freeze until every declared reviewer has submitted one canonical `COMPLETED` receipt that matches that assignment. Missing, failed, incomplete, stale-head, wrong-scope, or wrong-thread receipts deny freeze without consuming another cohort.
  - Proposal-only model boundary: Codex App Server parents and children are identity and proposal workers only. They run read-only with network disabled, `approvalPolicy=never`, `dynamicTools=[]`, no MCP servers, no hooks, no inherited tool environment, and no exposed command or file-mutation approval. Native thread evidence never grants write authority, and model-provided roles are ignored.
  - Exact runtime action boundary: A reviewed deterministic supervisor and a distinct broker principal may authorize only one presealed replacement of one existing tracked file. The canonical grant must bind the exact case, controller-assigned implementer thread and completed turn, repository, branch, worktree, base head, target path, baseline and replacement digests, controller receipt, worker and broker SIDs, expiry, isolation evidence, and pinned controller sources. Parent, reviewer, closure, incomplete, and unknown identities receive no mutation grant.
  - Operating-system enforcement: The target, canonical state, controller source, and dedicated nonoverlapping proposal roots plus their immediate parents must be broker-owned and explicitly deny the worker write, delete, delete-child, permission-change, and ownership-change capabilities. Root creation, nested creation, exact-anchor overwrite, replace, rename, delete, hard-link, ACL-change, and owner-takeover probes must all fail with access denied while challenge paths remain absent and anchor hashes, identities, and security-descriptor hashes remain unchanged.   - Active-grant barrier and recovery: While one grant is issued or claimed, unrelated case mutations are denied without revision change. A broker restart may resume once only from protected journal evidence and an exact baseline, or complete an already exact replacement without rewriting. Any mismatch, second recovery, preclaim failure, supervisor-context loss, rollback failure, or attempted replay consumes the grant and locks only that case. No grant is released or reissued.
  - Access-control transaction and startup gate: The broker must journal the exact original descriptors and lockdown intent before changing any protected access control list, keep lockdown active through post-replacement dual-profile probes and canonical completion, then restore parents before children. Startup must resolve pending lockdown, active-grant, completed-grant, and partial-restore state before schema inspection or App Server launch. A no-grant case may start only from `IMPLEMENTING`. Quarantine preserves all lifecycle counters, writes an exact protected backup and hash-chained audit, never reopens the case, and records whether external reconciliation is required.
  - Narrow scope: The single-file replacement broker is feasibility coverage for this exact primitive. It is not authority or evidence for arbitrary commands, file creation, deletion, rename, multi-file patching, general coding, publication, merge, deployment, credentials, or universal synchronization.

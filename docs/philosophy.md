# Philosophy

Codex Coding OS starts with the customer outcome. A founder should be able to
explain the change they need, approve consequential choices, and see whether
the delivered software does what they asked.

The agent reads existing requirements and architecture, looks for reusable
solutions, and prepares routine engineering details. It asks about unresolved
customer behavior, priorities, spending, commitments, and consequential
external actions. Approved choices remain in force until relevant facts
change. A file path, library choice, identifier, or test command becomes a
founder question only when the choice changes a business consequence.

Ordinary Codex tasks remain appropriate for small changes. Campaigns serve
work that benefits from durable state and bounded delivery across sessions.
The additional machinery has to earn its place through accepted results.

The user approves one complete immutable contract. A pure reducer decides every
lifecycle transition. A durable store serializes those decisions. A
deterministic supervisor chooses only from the approved finite graph. Workers
receive the smallest effective execution boundary. Evidence and external
effects remain explicit and exact-head bound.

A recognized acceptance failure can consume one declared correction allowance
when the original scope, evidence, authority, and remaining budget still match.
Independent reviewers then check the requested business behavior against the
frozen candidate. Blocking defects require evidence of an unmet acceptance
expectation, broken invariant, or reproducible regression. Nonblocking
observations stay visible without opening another repair cycle. The existing
combined repair and closure limits remain final.

Recovery uses attested results and observable surviving work. It never resets
attempts, forgets expenditure, or revives a cancelled campaign. When an external
action has an uncertain outcome, the engine queries that action before deciding
what can happen next. When evidence is insufficient, it stops with a reason.

One executable engine owns this lifecycle. Skills, documentation, hooks, and
adapters prepare work or explain evidence. They cannot invent transitions or
become additional controllers. Workers receive only the context and tools
needed for their approved task.

Repository mirrors remain useful for human context, but current lifecycle state
belongs outside Git. Product evidence, engine status, and process status are
reported separately so one cannot impersonate another.

Maintain lasting documentation when product behavior or an accepted decision
changes. Use one coherent pull request for a coherent change. Reading progress
does not justify a status document, another commit, or another pull request.

Measure actual input and output tokens, accepted behavior, and founder
interventions. Include unsuccessful attempts and mark missing telemetry as
unavailable. Cached and reasoning tokens are subsets of reported usage, not
extra totals. A smaller prompt is useful evidence about context size, but it
does not establish lower total cost or better outcomes.

The controlled native delivery journey demonstrates the implemented workflow.
Independent adoption and comparative improvements need separate trials. A
dashboard, hosted service, or paid tier should follow measured customer need.

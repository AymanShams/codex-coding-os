# System Scope

Codex Coding OS provides:

- immutable campaign contracts
- source-linked acceptance preparation and routine engineering value derivation
- one pure lifecycle reducer
- one external SQLite authority store
- exact repository and installed-runtime admission
- deterministic supervision and finite dependency selection
- native bind-before-turn workers with scoped writes
- trusted validation execution
- exact-head review and one combined repair
- one bounded correction for a recognized acceptance assertion failure
- recorded nonblocking observations without another repair cycle
- idempotent publication effects with ambiguity reconciliation
- durable cancellation and restart recovery
- recovery of an existing read-only review turn through its surviving host connection
- measured native token usage with explicit telemetry coverage
- transactional installation and runtime-pin verification
- read-only legacy archival
- thin repository adapters and exact CI signals
- dormant, public-safe canonical capability-router reference source and schemas
- provider-aware security routing decisions for Codex Security, Supabase, Neon
  Postgres, generic PostgreSQL, and frontend work
- bundled provider-neutral security and PostgreSQL guidance

It does not provide a second lifecycle engine, repository-state authority,
caller-declared role authority, hidden fallback mode, automatic successor
campaigns, unbounded polling, or blind retries of uncertain mutations.

It also does not install or activate the dormant router, write a universal
route registry, ship private project mappings, copy Codex Security plugin
skills, manage provider credentials, or prove live Supabase or Neon state from
static source inspection.

Skills and documentation remain available as knowledge and drafting tools. They
do not own campaign lifecycle decisions.

The product hypothesis is that a founder or small team can delegate a specified
change with fewer unnecessary interventions while retaining clear evidence of
what completed. Native Codex is the first comparison baseline. Its existing
agents, worktrees, skills, and scheduled work overlap with parts of this package.

Reducer tests, incident replays, and simulated worker or provider fixtures prove
the behavior they execute. Public continuous integration checks also exercise
package installation and validation boundaries on Windows, Linux, and macOS.

The product delivery work completed a controlled public-install journey on
Linux with real Codex workers. It exercised preparation, admission, approval,
an intentionally faulty first proposal, a real failed acceptance test, bounded
correction, two independent reviews, recovery of the same review turns, and one
confirmed push to a disposable bare Git repository. The delivered program was
then checked independently against normal orders, refunds, zero-value orders,
and empty input. Reinstallation and removal preserved the external state.
The [delivery pull request](https://github.com/AymanShams/codex-coding-os/pull/48)
records the candidate and validation evidence.

This controlled journey proves that supported local delivery path. It does not
establish independent customer adoption or a real GitHub publication through
the automated campaign. Native model execution was exercised on Linux. The
Windows and macOS checks cover installation and controlled validation, not a
complete native model journey on those platforms. Lower token cost, fewer
founder minutes, and comparative superiority remain unproven until measured on
matched tasks, including unsuccessful attempts. Missing usage stays unavailable.
